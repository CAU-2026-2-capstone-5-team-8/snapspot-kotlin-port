# SnapSpot 프로토타입 계획: 지도 매핑과 위젯

> 이 문서는 팀 저장소 `snapspot`의 `docs/overview.md` 중 **"10/13기준 추가 사항" 이후**만 옮긴 것이다(2026-10-13 작성 시점의 내용). 그 앞부분(프로젝트 개요, 핵심 문제와 해법, 검증 결과, 현재 구성)은 옮기지 않았다.
> 위젯은 아직 **구상 중**이고, 지도 매핑은 프로토타입까지 만들었다. 진행 상황은 [prototype-map.md](prototype-map.md), [prototype-widget.md](prototype-widget.md)에 있다.

## 10/13기준 추가 사항

### 배경: 알림만으로는 부족하다

- 알림 권한을 허용하지 않으면 알림이 갈 수 없다.
- 하루에 알림을 너무 많이 받는 사용자는 SnapSpot 알림이 다른 알림에 밀려 보지 못한다.

그래서 알림은 보조 수단으로 두고, 알림 없이도 보이는 경로 두 가지(위젯, 지도 매핑)를 추가한다.

단계별 계획과 진행 추적은 기능마다 따로 있다: [지도 매핑](prototype-map.md), [위젯](prototype-widget.md).

### 구현 전 상태 (Kotlin 앱 기준)

아래는 지도 매핑 프로토타입을 만들기 **전**의 상태다. 구현 뒤의 모습은 [prototype-map.md](prototype-map.md)에 있다.

- 지도 탭(`ui/map/MapRenderer.kt`)은 저장한 장소를 전부 그린다(핀, 반경 원, 끝난 장소 포함). 쿠폰 지점 배지는 지오펜스로 등록된 근처 지점(`WindowState.branches`)만 그리고, 누를 수 없다.
- 쿠폰에는 좌표가 없다. 위치는 카카오 지점 검색(`domain/BranchFinder.kt`의 `nearbyBranches`, `branch_cache` 6시간 캐시, 0.01° 격자)으로만 얻는다.
- 위젯 의존성(Glance)은 없다. `snapspot://coupon/{id}`, `snapspot://place/{id}` 딥링크는 이미 있다.
- `WindowRepository`(DataStore)가 현재 감시 창을 저장하므로 위젯이 읽을 수 있다.

### 1. 지도 매핑 (멘토님 제안)

앱을 열면 가 보고 싶었던 장소와 쿠폰을 쓸 수 있는 지점이 지도에 한눈에 보인다. 장소는 이미 전부 표시되므로 부족한 부분만 채운다.

**조회 방식** (감시 창과 분리한 지도 전용 조회. `nearbyBranches`와 `RoomBranchCache`를 그대로 쓴다):

1. 지도에 처음 들어올 때 현재 위치 기준으로 쿠폰 지점을 조회한다.
2. 위치는 지도 화면이 열려 있는 동안만 추적한다(내 위치 표시, 자동 재조회). 자동 재조회는 처음 조회한 범위를 벗어났을 때만 한다. 앱이 꺼져 있을 때의 알림용 감지(감시 창, 갱신 구역)는 기존 방식 그대로다.
3. 사용자가 지도를 밀거나 축소하면 "이 지역에서 다시 탐색" 버튼을 띄우고, 누를 때만 조회한다. 너무 축소된 상태면 버튼 대신 "확대해 주세요"를 안내한다.

**호출 수 제한**: 디바운스는 쓰지 않는다. "다시 탐색" 버튼, 줌 제한, 기존 캐시(6시간, 약 1km 격자) 재사용으로 제한한다. 카카오는 질의당 최대 45건이고 조회 단위가 브랜드×격자라서, 자동으로 조회하면 요청이 브랜드 수 × 칸 수만큼 늘기 때문이다.

**배지와 쿠폰 연결**:

1. 지점 배지를 쿠폰과 연결하고, 누르면 쿠폰으로 이동한다(`MapScene`, `MapRenderer` 확장). 지금 `BranchRef`에는 `brandKey`만 있고 쿠폰 id가 없으므로, `brandKey`로 `couponsForBrand`(활성 쿠폰만, 만료 빠른 순)를 불러 쓴다.
2. 같은 브랜드 쿠폰이 여러 장이면 만료가 빠른 순으로 목록 맨 위에 보여 주고, 1장이면 바로 쿠폰 상세로 이동한다.
3. 활성 쿠폰만 표시하고(`isActive`), **끝난 장소는 지도에서 뺀다**(`suppressReason`이 ENDED. 함수는 `domain/NotifyPolicy.kt`에 있고 `ViewRules.kt`가 `placeFacts`에서 쓴다). 흐리게 표시하지 않고 저장 목록(장소 탭)에서는 지우지 않는다. 구현 전에는 지도에 넘기는 장소 목록이 끝난 장소를 거르지 않고 모두 그렸다.
4. 필터 토글: 장소 / 쿠폰 / 둘 다 (프로토타입에서는 제외).
5. 지점이 많을 때: 표시 개수 상한 또는 클러스터링 (프로토타입에서는 제외).

열린 질문: 한 번에 몇 개까지 그릴지, 브랜드가 여러 개일 때 색을 어떻게 구분할지, 줌 제한 값(프로토타입은 13으로 시작), "처음 조회한 범위"의 크기(약 1.5km로 시작). 둘 다 실제 기기에서 조정이 필요하다.

### 2. 위젯 (구상 중)

알림을 못 받거나 놓쳐도 홈 화면에서 지금 쓸 수 있는 것을 본다. 표시 내용은 아직 정하지 않았다.

| 후보 | 내용 | 비고 |
|---|---|---|
| 근처 쿠폰 | 가장 가까운 쿠폰 지점, 거리, 만료일 | 위치 갱신 필요 |
| 곧 만료되는 쿠폰 | 만료 임박순 1~3장 | 위치 불필요, 구현이 가장 쉬움 |
| 가 볼 장소 | 가까운 순 또는 종료일 임박 장소 | |
| 지도 미니뷰 | 정적 지도 이미지 | 카카오 SDK와 맞지 않고 비용이 큼 |

- 기술: Jetpack Glance(`androidx.glance:glance-appwidget`)를 추가한다. 데이터는 Room(쿠폰, 장소)과 DataStore(`WindowRepository`)에서 읽는다. 갱신은 WorkManager와, 쿠폰 저장·사용 처리·재계획 시점의 `updateAll`로 한다. 탭하면 기존 딥링크로 이동한다.
- 제안: 1차는 "곧 만료되는 쿠폰 + 근처 지점"의 소형/중형 위젯, 위치는 감시 창의 마지막 위치를 쓴다.
- 프로토타입에서는 거리 숫자 대신 "근처 지점 있음"으로 표시한다. 감시 창의 위치(`WindowState.here`)는 현재 위치가 아니라 계획을 세운 위치(갱신 구역의 중심)라서, 거리를 숫자로 보이면 최대 약 1km 어긋날 수 있기 때문이다.
- 열린 질문: 위젯 크기 종류, 위젯이 위치를 직접 갱신할지(배터리 영향).

### 우선순위와 일정

- 지도 매핑과 위젯 모두 프로토타입 범위로 진행한다.
- 지도 매핑을 먼저 한다(기존 코드를 많이 재사용하고 멘토님 요청이기 때문). 위젯은 그다음이다.
- 7단계(권한 요청 흐름)에서 알림을 거부한 사용자에게 "위젯과 지도로도 볼 수 있어요"를 안내하도록 연결한다.
- 2026-10-16 중간 발표 전에는 문서화와 지도 매핑 범위 결정까지 하고, 구현 시점은 팀과 확인한다.

### 검증 방법 (구현 시)

- 지도: 에뮬레이터에서 쿠폰을 저장하고 앱을 열어 감시 창 밖 지점까지 배지가 보이는지, 배지를 누르면 쿠폰으로 이동하는지 확인한다. 지점 필터링은 JVM 테스트, 렌더링은 계측 테스트로 본다.
- 위젯: 에뮬레이터 홈 화면에 추가하고, 쿠폰을 사용 처리한 뒤 갱신되는지, 알림 권한을 끈 상태에서도 보이는지 확인한다.

### iOS 버전 방향 (Kotlin vs Expo)

> 이 절은 팀 저장소가 Kotlin으로 전환되기 전의 판단이라, 지금 상황과 다를 수 있다.

결론: Android는 Kotlin으로 계속 진행하고, iOS는 나중에 `domain` 패키지를 공유하는 방식으로 이어 간다.

- 핵심 기능(지오펜스, 앱이 꺼진 상태에서 깨어나기, 부팅 후 재등록, 위젯)이 OS 전용이다. 위젯은 Android는 Glance, iOS는 WidgetKit(Swift)으로 어차피 따로 만들어야 해서, Expo로 가도 네이티브 작업이 남는다.
- Kotlin 이식이 이미 6단계까지 끝났다. Expo로 돌아가면 그만큼을 버리게 된다.
- 지도 오버레이(카카오맵 SDK)는 네이티브 쪽이 세밀하게 다루기 편하다.

iOS 착수 시 선택지:

1. **(권장)** `domain`(순수 Kotlin)을 Kotlin Multiplatform으로 공유하고, iOS 화면·지오펜스·위젯은 SwiftUI로 만든다. 창 계획, 브랜드 필터, 장소 매칭 로직을 그대로 쓴다.
2. 기존 Expo 앱을 iOS용으로 키운다. TypeScript 로직은 이미 있지만 Android와 로직이 두 벌로 갈라져 기능이 어긋나기 쉽다.

주의할 점:

- iOS 지오펜스는 20곳뿐이다. 시뮬레이션에서 20칸 + 갱신 500m은 재현율 89.5%, km당 깨어남 1.18회로 Android(100.0%, 0.71회)보다 나빴다. iOS에서는 지도와 위젯 같은 알림 외 경로의 비중이 더 커질 수 있다.
- iOS 빌드와 출시에는 Mac과 Apple 개발자 계정(연 $99)이 필요하다. Expo를 써도 같다.
- 팀에 Swift 경험자가 없고 iOS를 빠르게 비슷한 기능으로만 내야 한다면 Expo가 나을 수 있다. 위젯과 지오펜스는 Expo에서도 네이티브 작업이 따로 필요하다.

지금은 `domain`을 플랫폼과 무관하게 유지하는 것만 신경 쓰고, iOS 착수 시점에 팀 인원과 일정을 보고 다시 정한다.
